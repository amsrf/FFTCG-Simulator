# Changelog

All notable changes to the FF TCG Simulator project.

## [Unreleased] — 2026-09-11

**Session summary.** Started from "there is no scene routing, no opponent turns, and no way to win a game". Now: a menu boots into a configurable match; turns alternate; both sides act through an `Agent` seam (human UI today, AI today, a networked player later); the AI plays cards, attacks with tap-economy judgement and blocks; the human can block; and a match ends at 7 damage. The biggest structural win was separating "parked" (awaiting its cost) from "legally on the stack" — that conflation was the root of a whole class of bugs. Along the way the `GlobalVariables` god-object was reduced to presentation state + input mode, and the leftover editor junk was swept out.

The session ended on presentation and tooling: the targeting cue became a **CSS-modelled glow ring** with a distance-graded fade and an orange selected state, the targeting arrow was **rebuilt from scratch** as a generated ribbon plus real arrowhead (with the origin finally coming from the right object — the effect card in the stack), and — the change most likely to matter long term — **Godot can now be run headlessly against a probe**, so geometry, wiring and invariants are verified with printed numbers instead of being described by eye. Taste still needs eyes; almost everything else no longer does.

### Things Learned the Hard Way (worth not repeating)

- **A screenshot beats a description, and a probe beats both.** `tools/shot.gd` boots a scene *with rendering*, lets it settle, saves a PNG and quits, so anything visual can be looked at directly:
  `godot res://tools/shot.tscn --quit-after 400 -- --preset ai --pay "fire:1,neutral:1" --cam-zoom 0.25 --out tools/shots/x.png`
  Never pass `--headless` — there would be no rendering device and nothing to draw with. `--preset` boots the real game through `MatchSetup`, `--pay` opens a payment modal at a known cost, `--cam-zoom` magnifies a detail (and re-aims at the readout, because zooming about the screen centre throws a readout that sits low straight out of frame), `--out` picks the file. This found three faults in one session that reading the code had not: a readout in the wrong place, a badge too small to read, and a numeral that was never drawn at all. Its output is gitignored; the tool is not.
- **Size and check VISUALS at game scale, never against a framed asset shot.** An asset shot fits the subject to the frame, so it flatters everything: the cost badge looked right there and was ~41 px in play, which made its 1-px ring and half-size numeral invisible — a cost read as "Pay [flame] [black dot]". Shoot both ways, the real camera *and* a zoom, and compare. The numbers worth remembering: the match camera is orthographic with a 5.766 m vertical extent over 1080 px, so **187 px per metre**, and screen-up is `0.985 * +z + 0.174 * +y` — which is why "above the hand" is nearly all z.
- **A `Label3D` that renders in an asset scene may not render in the game at all.** A numeral built as a `Label3D` was verified correct in every respect — `text='1'`, `visible=true`, the right `pixel_size`, correct parenting, billboarded, `no_depth_test` — and a 4× zoom shot of its badge showed a blank disc. The cause was never established, and that is recorded here honestly rather than dressed up as a diagnosis. The fix was to stop depending on it: digits are baked as **textures** drawn on the quad, riding the same path the element glyphs already prove works in both contexts. Text that must appear in-game should be a texture.
- **`remove_child()` before `queue_free()` when rebuilding children.** `queue_free()` is deferred to the end of the frame, so the old nodes still answer `get_children()` — which is how a rebuilt cost row ended up holding two sets of badges. Removing from the tree has to be immediate; freeing can wait.
- **A setter only runs when something ASSIGNS the property.** "Pay" was sized from the badge size inside a setter, which felt self-maintaining and did nothing at all: nothing ever assigned it, so the old default stayed in force and the word towered over the icons it introduced. If one value must track another, assign it explicitly at construction, or assert the relationship in a probe.

### Next Steps (suggested order)

1. **`DRAW_PHASE` on an empty deck should be a loss**, matching how `take_damage()` already reports running out of deck. Unreachable in practice (7 damage lands first), but it is a silent `return` of exactly the kind that has already caused bugs here.
2. **Per-combat resets are ambiguous.** `reset_attacker()` / `reset_blocker()` run after the phase they advanced into (see AGENTS.md), so the blocker arm re-resets at its start. Worth restructuring so the reset has one unambiguous moment — and `reset_attacker()` also never clears `set_attacker_status(true)`'s `'attacking'` flag / z-offset, unlike the guarded `reset_blocker()`.
3. **The AI cannot start from an empty board.** `AIAgent.pay_cost()` taps only Backups, while the human may also pay with cards from hand (worth 2 mana each). So on `standard` (no pre-placed Backups) the AI can never afford its first card and the match stalls — that is why `standard` still uses the `mock` opponent. Either teach `pay_cost()` hand mana, or give both sides a starting setup.
4. **`choose_card_in_hand()` is still unwired** — `Game._resolve_may_play_for_free()` and `Stack.begin_s_cost_selection()` own that modal directly.
5. **Richer card effects.** `activated_ability` in `card_effects.json` is unwired, `END_PHASE` has no priority window (so end-of-turn auto-abilities can't resolve before cleanup), and `card_effects.json` still covers only a handful of cards.
6. **The opponent's hand is face-up**, which undercuts the new reveal timing: a parked card is hidden while the very same card is visible in their hand. Hide the opponent's hand to make it meaningful.
7. **State-refactor step 3** — replace the remaining `Player_Mode` comparisons with capability queries, and add a `phase_changed` signal so readers subscribe instead of sampling.
8. **The arrow's impact burst.** The reference (`references/tip.png`) lands the arrow in a small golden starburst at the target; today it lands in a plain arrowhead. Cheap to add as a short-lived radial burst at the tip.
9. **Targets are chosen as the ability goes on the stack**, not when it resolves (`Field.execute_card_effect()` → `request_target()`, with the chosen target stored on the stack card). That matches the rules as understood, but it means the prompt opens while the effect card is still tweening into the stack — which is why the arrow follows it in. If a settle-then-prompt feel is preferred later, that is a change in `Field`/`Stack`, not in the arrow.
10. **Leftovers to delete when convenient:** `arrow.gd` and `Blender/pyramid.obj` (dead since the arrow stopped using a pyramid head), and the invisible `Target` node inside `card.tscn` plus `target.tscn` itself (dead since the per-target marker was removed).
11. ~~Extend the probe to the targeting flow end-to-end~~ — **done.** `tests/flow_probe.tscn` boots the `ai` preset, fires an ETB and asserts the arc's source is the **stack's effect copy**, that `set_viable_targets()` marks exactly the Forwards, and (mesh-verified) that the review link is drawn at the right card. There are now four probes: `flow`, `block`, `arrow` and `button`.
12. **Gem button polish** — it is in and working; these are refinements:
    - the preview camera (`GemButtonPreview.tscn`) was framed for the bare model, so re-aim it now that the button carries text.
    - the text quad sits 0.02 above the button face (copied from `BigButton`); over a dome that may read as slightly floaty — drop it to ~0.005 if so.
    - the gem's Blender-side `roughness` and `STONE_EMISSION` (0.15 / 0.35) affect only the Blender render. In Godot the stone is `shaders/gem_button.gdshader`, tunable live in the Inspector (`emission_strength`, `roughness_value`, `rim_strength`).
    - `Blender/capsule_gx_f.glb` and `Blender/button_idea.blend` are no longer used by the game (the generator supersedes them) — keep as reference, or delete.
    - the metal's hover cue is the stone's glow (`gem_button.gd`); if a stronger hover is wanted, a slight roughness change or a brighter `HOVER_EMISSION` is the lever, not the albedo.

### Added

#### Decks, Summons and Reveal Timing
- **Seeded shuffle.** `MatchSetup._standard()` shuffles each deck with a dedicated `RandomNumberGenerator` (`_shuffled()`, Fisher-Yates) *before* slicing the opening hand, and records the seed in the config (`_pick_seed()` invents and prints one when it is 0). `Array.shuffle()` was deliberately avoided: it uses the global RNG, so the match could not be reproduced from the config. The `ai` / `debug` presets keep `shuffle: false` so their hand-picked practice boards stay deterministic.
- **The AI casts Summons.** `AIAgent._is_safe_to_play()` now allows a Summon when a legal target exists (`Field.has_viable_target(criteria, card, "Summon")`), which exercises the non-local targeting path (`Field.request_target()` → `Agent.choose_target()`) for the first time. `AIAgent.pay_cost()` also taps element-matching Backups before off-element ones — every Backup can pay generic cost, so spending an off-element source early starved later plays.
- **Reveal timing.** `Card.set_revealed()` shows the art or a plain back (there is no back-art asset), and `Stack.park_card()` hides every card the local player does not own — a cost being paid is not public knowledge. `reveal_parked()` covers all four exits: `cast_card()`, `_commit_summon_to_stack()` and both cancels.
- Fixed: `Stack.hand` is `Player/Hand`, so `_commit_summon_to_stack()` / `_on_assistant_target_cancel()` routed an **opponent's** Summon through the local player's hand, leaving a stale `charging_card` there that `Hand.cancel_summon_cast()` could later use to pull the card back off the stack. Both now go through `Stack._owner_hand(card)`.

#### Selectable / Targetable Card Glow
- **`shaders/target_border_material.tres` is the look.** Open it in the editor and every uniform of the shader shows up in the Inspector with sliders / colour pickers; `Card._build_target_border()` duplicates it per card and overrides only `card_size` (read from the mesh) and `intensity` (the fade). `margin` is read back out of the material to size the glow quad, so there is **no** constant in GDScript left to keep in sync — tuning the `.tres` is enough.
- **`shaders/target_border.gdshader`** — the glowing blue ring marking a card the game is asking the player to choose or target, modelled on `references/target_border.png`. A rounded-rect SDF evaluated in **world units** over a quad slightly larger than the card, so the light sits outside the edge and never overlays the artwork: two-lobe falloff (a thick core plus a wide halo), `blend_add` so it reads as a backlight, `depth_draw_never`, `unshaded`, and `cull_disabled` so it shows from either side. Card size comes from the mesh's own AABB (0.429 x 0.6 in the XZ plane), so the corner radius stays circular instead of being stretched by the aspect ratio. Second pass: deeper and more saturated `glow_color`, `core_heat` keeping the whitening off the line, thicker `core_width` / `halo_width`, and a visible `pulse_amount`.
- `Card._build_target_border()` builds the quad in code (nothing to keep in sync in `card.tscn`), **parented to `HandMesh`** rather than to the Card so the hand's hover animation — which moves and scales the mesh, not the Card — carries the glow with it. `Card.set_highlight(bool)` is the only entry point and fades in/out, skipping unchanged requests because it is called from the hand's layout path.
- **Prompt-driven only.** The glow means "the game is asking you to pick this", never "you could play this":
  - **Field** — `Field.set_viable_targets()` / `reset_targets()` → `Card.set_valid_target()`: every legal target glows for the duration of a targeting session, while illegal ones stay dark (so `cannot_be_chosen` is visible).
  - **Hand** — `Hand.refresh_highlights()` glows only during `CHOOSE_CARD_IN_HAND`, and only for the cards that satisfy the criteria (all Fire Backups for Auron's trigger). A normal main-phase hand stays completely dark; the earlier "playable cards glow" behaviour was a misreading of the requirement and has been removed.
- **Hand fan, and a height stagger that fixes the glow bleed.** `Hand.calculate_card_position()` now spreads the hand along a **shallow arc** (`FAN_RADIUS`, 2.4 m) with each card tilted by `fan_angle_for(i)` instead of forming a straight row, and separates cards by `CARD_STACK_HEIGHT` (8 mm) in height. The old layout lifted each card by only 1 mm — *less* than the 2 mm the glow quad sits above its own card face — so the prompt glow of a card behind showed through the card lying on top of it. `CARD_STACK_HEIGHT` must stay above 2 mm. The tilt is the **negation** of the arc angle used for the positions (a fan radiates outward, and the card's up axis is its local −Z), so the two must be flipped together or the fan reads as closed — which is exactly how the first implementation looked.
- **Zone presentation is now standardised on `Card.enter_zone()`.** Cards were carrying one zone's look into the next: `Field.play_card()` preserved the whole `global_transform` (so a card played from hand kept the hand's new fan tilt), the animated and non-animated play paths set *different* field scales (1.4 vs 1.2), and `Graveyard.add_card()` set only a position — so a broken Forward arrived in the graveyard tilted, oversized and still wearing its power/accumulated-damage readout. `Card.Zone` + `Card.ZONE_PRESENTATION` now hold one table of per-zone scale / rotation baseline / readout visibility, and `Card.enter_zone()` is the single entry point: it normalises rotation and scale and clears the drag flag, target glow and mana crystal. Called from `Field.play_card()`, `Graveyard.add_card()`, `DamageZone.add_card()`, `Stack.park_card()` and `Hand.add_card_to_tree()`; zone layouts still own positions.
- **The graveyard is a proper pile.** `Graveyard.update_card_positions()` used `position += ...` (drifting further away on every call) and `add_card()` never called it, so every card sat at position zero on top of each other. It now assigns absolute positions with the newest card on top and un-scattered, the older ones taking a small index-seeded scatter so re-laying out cannot make the pile jitter.
- A freshly drawn card now lands on the **fan tilt** instead of tweening its rotation to zero, which left it lying flat in a fanned hand.
- Fixed: **the first cut of `enter_zone()` put every field card upside down.** Zeroing the local rotation was wrong because a card's baseline is *not* zero — cards read correctly a half turn about Y from the identity frame (`Card.READABLE_ROTATION`), and the `Hand`, `Stack`, `Graveyard`, `Deck` and `FocusCard` nodes each supply that flip through their own scene transform (-1 on X and Z). `Field` is a plain identity node, so its cards must carry the half turn themselves — which is exactly what the old `play_card()` was inheriting from the hand's global transform without anyone noticing. The baseline is now per-zone data (`"rotation"` in `ZONE_PRESENTATION`) instead of a hardcoded zero.
- **The glow was re-modelled on CSS, because "thickness" was not expressible before.** The two-exponential-lobe falloff had no edge — `core_width` moved a soft gradient inside a halo whose real extent was set by `margin` — so no parameter visibly controlled how thick the ring was, and tweaks looked like they did nothing. Now the ring is a **solid band**: `border_width` (metres, from the card's edge outward) is the thickness knob, `border_color` its colour, `border_feather` how soft its outer edge is, and `glow_width`/`glow_color` are the spill past it (CSS `border-width`/`border-color` + `box-shadow` blur/colour). `Card._build_target_border()` now **derives** the quad's margin from `border_width + glow_width * 3` and writes it back, so widening the ring can never be cropped by the quad — the failure mode that had been silently limiting every earlier attempt — and `get_shader_parameter()` returning null (→ `float(null)` = 0.0) can no longer collapse the quad onto the card. Over-exposure is gone with it: the band is the colour at `border_gain` rather than a 2.5x multiplier over it, so the blue channel clips while green stays low — saturated blue instead of cyan-white. A one-shot console line reports the values actually in use (`[TargetBorder] card=… quad=… border_width=… border_color=…`).
- **The ring is solid now, its pulse drives width *and* brightness, and the card you picked turns orange.** Blending moved from `blend_add` to `blend_mix`: additive light always merges with whatever is behind it, which is precisely why the ring kept washing out toward white over bright artwork, whereas alpha lets the ring *replace* the background and hold its colour — `border_alpha` (0.95) and `glow_alpha` (0.45) are the new opacity ("transparency") knobs. A single cosine wave now drives both pulses: brightness (`pulse_amount` 0.3) and a deliberately slight width swell (`pulse_width` 0.15) that re-evaluates the band each frame, so the ring breathes instead of flickering. And the card the player has actually PICKED gets the same ring in **orange** — `Card.set_selected_highlight()` swaps `border_color`/`glow_color` on that card's own material copy and restores the cached stock colours on deselect — so blue means "legal", orange means "this one". Wired to `Field.set_target_card()` for targeting, which now also MOVES the selection when another valid target is clicked instead of ignoring the click, and to `Hand.toggle_effect_card_selection()` for a chosen card in hand.

#### Headless Probes (`tests/arrow_probe.tscn`, `tests/flow_probe.tscn`, `tests/block_probe.tscn`)
- **Godot can now be run for verification**, which changes how much is checkable without the user. The probe instantiates a real `BallisticArrow`, drives its own functions directly (no mouse, no menu, nothing shipped) and asserts the facts that previously had to be judged by eye. First run, all green: `apexes 1 | inflections 0 | measured peak 1.20x` (exactly `peak_ratio`); the screen clamp engaging at `asked 6.00 → allowed 1.80` (431 px of headroom at the board centre, **199 px per metre**); `mesh surfaces 2`; `shaft 474 verts / 158 tris`, `head 6 verts / 2 tris`; the head's base `0.0010 m` from the nearest shaft vertex (= `edge_stub`, i.e. a zero gap); and the origin tracking its card 1:1 (a 0.50 m card move → a 0.500 m origin move) from the card's **top edge** (0.3 m off centre, at +Z).
- The exact command, and the trap that killed the earlier attempt, are recorded in AGENTS.md: `Downloads/Godot_v4.7.2-stable_win64.exe/` is a **directory** whose name ends in `.exe`, with the real binary one level inside it.
- **`tests/flow_probe.tscn` boots the real game** on the `debug` preset and drives the ETB → stack → targeting handoff by calling functions instead of clicking. It asserts today's bugs: the effect copy lands on the stack with `effect_source` pointing at the played card; the arrow's source is **that copy, not the field card**; exactly the legal targets are marked (`Zack, Squall, Squall` for `{"is_type": "Forward"}`); and the origin sits on the copy's top edge and **stays** there across the stack's 0.3 s tween — measured `(0, 0, 0.3) → (-3.76535, 2.06214, 0.9681)`, matching `get_global_top_centre()` to the last decimal. 9/9 checks pass.
- Fixed (found by the probe): `Hand`, `Stack` and `DamageZone` resolved their siblings through `get_tree().current_scene.get_node(...)`, which is only set when the game **is** the top-level scene — so under the harness eight `@onready` references came back **null** and the game ran half-wired. They now walk the tree (`get_node("../../Field")`, `get_parent().get_node("Player/Hand")`), matching what `Stack.field` and `Hand.graveyard` already did. That was a latent bug beyond the harness: any second instance of the game scene (a future self-play or preview) would have hit it. It also cannot be worked around from outside — assigning `current_scene` to a nested node is rejected with `p_scene->get_parent() != root`.

#### Blocking Cues (who chose what)
- **The block declaration now shows what is happening**, which it previously did not: picking a blocker had no visible effect beyond the card's small z-lift, and an opponent's block stayed invisible until it resolved. `Field.set_blockable(controller, enabled)` marks every card that could legally block with the **blue prompt ring** — the same vocabulary as targeting, meaning "the game is asking YOU" — and `Field.set_blocker_card()` turns the picked one **orange** (`set_selected_highlight`) and draws the block arc. The predicate is `Field.can_block()` (an untapped Forward), deliberately the same rule the click gate in `field_card_state.gd` applies, so everything that glows is also clickable. Reselecting before committing just moves the orange and the arc; clicking the same card again deselects; `reset_blocker()` clears the orange and hides the arc, so the link survives through the damage step and disappears with the combat.
- **An opponent's pick draws the arc alone — no blue ring.** The ring means "your choice", and their declaration is not one. `_enter_phase(BLOCKER_DECLARATION_STEP)` shows it for the non-local defender and holds it for `block_announce_time` (1.2 s, an Inspector knob) so the human can read it before the damage step.
- **The block arc is its own `BallisticArrow`** (`Field.block_arrow`), not a reuse of the targeting one, which belongs to a targeting session and follows the mouse. It runs **centre to centre**, aims once and locks — both cards are already on the field and neither moves while the declaration is open — and lowers `min_distance` to 0.15 m, because *adjacent* cards are the common case for a block.
- **Found by the probe: a cross-row link cannot bow along screen-up.** A block joins the two battle rows, so its chord runs straight **up the screen** — exactly the degenerate case `ballistic_arrow.gd` had documented and never actually hit. The "arch" then runs along its own chord: measured **1.535 m of ribbon for an 0.847 m span, peak 0.00x**, a long loop rather than an arc. New `BallisticArrow.bow_perpendicular` rotates the bow to stay perpendicular to the chord's screen direction — so a same-row link keeps the classic hop, a cross-row link bows sideways, and a flip keeps it bulging away from the board — and the block arc sets it with a shallow `peak_ratio` of 0.22. After: **0.808 m of ribbon for the same 0.847 m span**, peak **0.22x**, tip **0.0350 m** from the attacker's centre, which is exactly the `arc_height` lift — i.e. dead on the centre. `_check_shape()` now counts its apex along the bow axis instead of always along screen-up, or a sideways bow would have been reported as a malformed curve.

#### The Gem Button, Generated in Blender
- **`Blender/build_gem_button.py` builds the button parametrically.** Driven by `blender --background --python` (Blender 4.4 is installed on this machine, matching the `button_idea.blend` header), it constructs the bezel and the set stone, assigns materials and UVs, exports `Blender/gem_button.glb`, saves `Blender/gem_button.blend` for hand-editing, and renders two Cycles previews (`gem_button_front.png` for proportions, `gem_button_three_quarter.png` for the dome and material). Every dimension is a named constant at the top of the file, so tuning is one edit and one re-run. This is also how the result got *judged*: the assistant cannot see a viewport, but it can render and then look at the PNG — which is what caught all three errors below.
- **Error 1: a plate with the stone sunk into it hides the stone.** The first build put a dome 0.01 below a *solid* top face. Metal shows the environment, so the top reflected as one continuous surface and the render showed no gem at all. The frame has to be a **bezel** — a pocket is cut in it and the stone is set in the pocket, its apex 0.02 below the rim.
- **Error 2: a per-point RADIAL offset is not the normal.** Offsetting each outline point along its own radius is only correct on a stadium's end caps; on the straights it skews the band and folds the surface, which threw spikes and shards at both ends. Every ring is now an **offset stadium** — `stadium(hw+d, hh+d)` is the exact outward offset of `stadium(hw, hh)` — so rings correspond point-for-point. Geometry is now clean: no spikes, holes or end-cap faceting.
- **Error 3: lighting built for illumination instead of reflection.** A big emissive card was placed at `y = -4.5`, i.e. between the camera and the button — the render was a photograph of the light card. Then, with the cards moved, a near-black world crushed the whole lower half of the bezel to void, and the metal read as "black plastic wearing a chrome outline". Chrome needs a *gradient* to reflect, not darkness. The cards now sit **outside the camera's frustum** (16° × 9° half-FOV, so the metal mirrors them and the camera never sees them) and the world is a dim blue-grey.
- **Geometry**: a stadium 3.50 × 1.00 × 0.34, rim round-over 0.10, pocket 0.15 deep, dome rising to 0.02 below the rim — 864 frame verts and 769 stone verts, with normals and UVs (V running bottom→top, which `shaders/gem_button.gdshader` depends on for its vertical gradient).
- **Error 4: the STUDIO LIGHTS WERE IN THE GAME ASSET.** The generator builds the model and the preview studio in one scene, and the export ran with `use_selection=False` — so `gem_button.glb` shipped `SoftboxBack` and `SoftboxSide`, two **5.2-unit emissive planes**, alongside the button. In a match those would have been drawn as giant chrome planes lying across the board. It also silently broke the text fit, because `face_size()` started measuring the largest mesh under the model: the button read **2.038 m** instead of 0.392 m, so the fit's budget was ~2.7x too generous. Caught by `tests/button_probe.tscn`'s drift check (click box vs measured face), *not* by eye. Fixed by selecting `Frame` + `Stone` and exporting `use_selection=True`; the glb now contains exactly `['Frame', 'Stone']`. The lesson: an exporter's default is the WHOLE SCENE, so a build script that also sets up lighting must say what to export.
- **Text fit: three causes, not one.** (1) `BigButton._autofit_label()` is only called from `set_text()`, and `_ready()` never calls it — so a button whose text came from the scene kept the scene's **128 px** until something configured it. (2) Its budget was **85% of the TEXT VIEWPORT**, but the button's face covers only `1.372 / 2.048` = 67% of the text quad, so the budget was ~1.5x too wide. (3) It checked **width only** — no vertical budget existed. `GemButton._autofit_label()` now derives the budget from the button's real face (`face_size()`, read from the meshes' own bounds scaled by `Background.scale`, no global transform so it is safe in `_ready()`), checks both axes, applies explicit margins (10% per side horizontally, 14% vertically), and runs from `_ready()` so scene-authored text is fitted too.
- **Sizes: the button is 1.372 × 0.392 m** — twice the old 0.685 × 0.196 in both dimensions, keeping the reference's 3.5:1 shape. A non-uniform scale was rejected because it stretches the rounded end caps into ellipses; a *longer-but-not-taller* button needs `WIDTH` in the generator plus a re-import, not a scale. Collision box and the text quad's y (0.075, clearing the rim at 0.0666) were updated with it. With the face measured correctly, the fitted text is 401 × 89 px in a 549 × 141 px budget — the text height lands at ~45% of the button's height.
- **Self-assessment, and where it stands now.** The chrome reads — a bright highlight along the upper rim wrapping convincingly around the end caps — the gem is set in a pocket inside a continuous bezel, and there are no geometry defects. Judged from the render at the time: 7/10, with the two remaining items being material numbers only (the stone's roughness 0.15 → ~0.05 for a tight wet highlight, and its emission 0.35 → ~0.9 so it reads as lit from within — both single constants in the generator, and both only affecting the Blender render, since in Godot the stone is `gem_button.gdshader`). Since then the button was resized to 1.372 × 0.392 m and its text fitted properly, and Error 4 above was found and fixed, so that score needs re-earning against the new asset on the next run.
- **Wired in: the gem button replaced `BigButton` for all three match buttons.** `GemButton.tscn` + `scripts/gem_button.gd` (`extends BigButton`, so `assistant.gd`'s `BigButton`-typed references still hold), and `game.tscn`'s single `11_mfdv2` ext_resource now points at it — ConfirmButton, CancelButton and PassPhaseButton all become gem buttons with no other edit, because a saved instance override resolves by **node path** and `GemButton.tscn` keeps every path `BigButton.tscn` had. `tests/button_probe.tscn` asserts that explicitly (`BigButton has 9 node paths; missing from GemButton: []`) rather than trusting it, and the revert is that one line back to `res://BigButton.tscn`.
- **Two decisions that are not obvious and should not be "cleaned up":**
  - The `Background/MeshInstance3D` node under the model is a **placeholder with a 1 mm invisible plane and no material**. `BigButton._ready()` calls `get_surface_override_material(0)` on that path; with *no mesh at all* the call fails its index check and prints an error for every button created, and giving it the shared `gem_button_metal.tres` would let `_dim_to()`'s albedo tween dim **all** buttons at once (and persist that if the resource were saved). One invisible plane plus a null override avoids both.
  - Hover/disabled feedback is driven by the **stone's `emission_strength`**, not by `_dim_to()`. Dimming a full metal's albedo is invisible — metal has almost no diffuse response — whereas "lit teal stone → grey unlit stone" is exactly how the reference depicts enabled vs disabled. `gem_button.gd` overrides the hover/unhover/`set_disabled` hooks for it.
- **Why the finished button still read as PLASTIC, and the fix.** Three separate causes, all measured before touching anything:
  - **A flat mirror reflects exactly ONE direction.** The face is flat and the sky is a smooth gradient, so the whole face sampled a single point of it and came back one uniform colour — and uniform *is* plastic. The reference's bright-top/dark-bottom look is art direction a UI artist baked in; no `StandardMaterial3D` value could ever produce it on a flat plate.
  - **The sky's ground was `0.02`, i.e. black**, so every surface facing sideways or down mirrored black — the rim's lower band, the outer wall, the underside. That was "the bottom of the button is all black".
  - **The plate was too thick.** 0.34 Blender units against a face height of 1.0 made it a third as tall as it was wide, so from the match camera (11° off vertical) its wall projected as a visible band.
  Fixes: the frame is now `shaders/gem_button_frame.gdshader` — still `METALLIC = 1.0` (so sky, lights, specular and fresnel all still apply) but with a **baked top-to-bottom ramp** in albedo and roughness, exactly the decision made between "baked ramp on real metal" and "fully stylized"; the sky's ground is lifted to `0.10` with a `0.30` horizon (luminance ratio now 8.7×, still unmistakably a studio gradient); the plate is **0.20 thick** with BEVEL 0.075 and POCKET_DEPTH 0.12 (BEVEL must stay under THICK/2 or the round-over pokes through the underside); and the stone's `bright_spread` went from **1.15 to 0.62**, because a "bright zone" that wide covered the whole face — the gem was flat for the same reason the frame was.
  The ramp axis is `UV.y`, and **`UV.y = 0` is the TOP of the button** as the player sees it: the unwrap runs along Blender's +Y, the glTF +Y-up conversion sends that to −Z, and screen-up for the match camera is +Z. Verified, not assumed — the three buttons in `game.tscn` have identity rotation, so the face points straight up.
- **Disabled = grey gem, and only the gem** (the design decision): the stone shader gained `grey_mix`, which desaturates `stone_deep`/`stone_bright`/`rim_color` toward their luminance and drops the emission, so the stone keeps its gradient and fresnel rim — the same object unavailable rather than a different object. The frame stays polished chrome. `GemButton` animates `grey_mix` and `emission_strength` together through one setter (`_set_hover_t` / `_set_disabled_t`), so the two parameters cannot disagree, and applies values directly when the node is outside the tree (which is also what lets the probe exercise the state).
- **Caught while wiring it up: the materials were SHARED.** `GemButtonModel` assigned the `preload`ed `gem_button_metal.tres` / `gem_button_stone.tres` directly, so a button writing `grey_mix` would have greyed **every** button at once and persisted it into the `.tres` on disk. It now `duplicate()`s both per model, and `tests/button_probe.tscn` asserts a second button's stone is unaffected.
- **Caught by the probe, not the eye: Confirm and Cancel overlapped.** They are separated *along z*, where a 1.372 × 0.392 button measures 0.392 — and at z = −2.0 / −2.35 the plates overlapped by 4 cm once the width doubled. Moved to −2.47 (a 5.8 cm gap). The probe's original check was wrong too: it demanded 1.372 m of separation regardless of axis, so it now does a proper AABB separation test (`gap_x >= 0 or gap_z >= 0`) and only asserts the pair that can actually be on screen together.
- **The gem needed the same treatment the frame got: a VERTICAL ramp.** The report was "it does not feel like a gem, it is just too uniform, the bottom needs to be darker than the top", and the cause was structural — the shader's bright zone was a **radial** core centred near the middle with a wide spread, so it washed most of the face. It is now a three-stop vertical ramp (`stone_crown` → `stone_body` → `stone_deep`, measured luminance **0.855 → 0.067**, a 12.8× falloff) plus a tight hotspot just under the crown and the existing fresnel silhouette. `bright_centre`/`bright_spread` are gone; `crown_stop`, `ramp_curve`, `highlight_y`, `highlight_r` and `highlight_boost` replace them. `grey_mix` still desaturates the whole ramp, so the disabled stone keeps its gradient.
- **Vertical centring bug: a stale offset, not a stale text value.** The text looked off-centre vertically because `Background`'s y offset was still `-0.17 × 0.392` — the value derived from the **old 0.34-thick plate** — while the model's top face had moved to `+0.10` after the plate was thinned to 0.20. So the whole button sat 0.027 m low and the text quad, still lifted 0.075 to clear a rim that is actually *below* the face, floated 0.10 above the surface. With the camera 11° off vertical that reads as a ~4% upward shift. Fixed to `-0.10 × 0.392 = -0.0392` and the quad to 0.012; `GemButton.face_height()` now exposes the relationship and `tests/button_probe.tscn` asserts the face lands on y = 0 (`sits at y = -0.0000`). **The lesson: when a generator changes a dimension, every constant derived from it has to be re-derived — the thickness change silently invalidated a number in a different file.**
- **Two runtime/parse errors of my own, both from the same animation helper.** `_animate_to()` called the setter with **no arguments** to read the current value, which raises `Expected 1 argument(s)`; and the replacement used `tween_property()` with a **StringName** where it requires a **NodePath**, which failed at parse time and took the whole script down — every button in the scene then became a plain `Node3D`, so the probe's "GemButton is a BigButton" check failed as a cascade. The states are now *properties with setters* (so every write funnels through `_apply_stone()` and the two parameters cannot disagree) animated with `tween_property(self, ^"_hover_t", …)`, and values are applied directly when the node is outside the tree.
- **The ramp was UPSIDE DOWN, because a UV convention was trusted instead of measured.** Both shaders ramped on `UV.y`, justified by a chain of reasoning ("the unwrap runs along Blender's +Y, the glTF +Y-up conversion sends that to −Z, screen-up is +Z, therefore UV.y = 0 is the top"). That chain has a hole in it: **Blender writes UVs V-up while the glTF exporter flips V**, so the axis was exactly reversed and the gem rendered dark on top. Both shaders now ramp on the **mesh's own +Z**, taken from `VERTEX` in the vertex shader, which has no convention to get wrong. `tests/button_probe.tscn` asserts the assumption against the scene rather than restating it: the camera's up axis `(0, 0.174, 0.985)` versus the button's +Z `(0, 0, 1)` → alignment **+0.985**.
- **The gem's palette is now SAMPLED from the reference, not invented.** `references/button_idea_reference.png` was read for its actual ramp, which corrected a wrong assumption: the gem is a **cool teal (hue ~174°), not a grass green** — `#EAFEFB` at the top through `#6FD8D0` and `#2BA79E` to `#03332C` at the bottom. Equally important, the bright area is a **horizontal band spanning the width**, dimming only ~10–15% toward the rounded ends, not a centred radial hotspot — so the shader shifts the ramp *down* toward the ends (`end_shift`) rather than using a radial falloff, which is what makes the white read as central and the ends as greener. `stone_top`/`stone_upper`/`stone_mid`/`stone_deep` with `crown_stop` 0.25 and `mid_stop` 0.45 reproduce that table; measured ramp **0.982 → 0.158**.
- **`face_span` guards the same staleness that bit the `Background` offset.** The ramp is normalised by a model-space height, and the stone's mesh spans only 0.826 of the face, so the stone's material declares `face_span = 0.826`. A hard-coded span goes stale the moment the generator is re-run, so the probe asserts it against the mesh's real extent (`stone mesh spans 0.826 in z; the material declares face_span 0.826`).
- **"The green is still too light" — because a reference image is FINISHED PIXELS, not an albedo.** The palette had been sampled straight off `references/button_idea_reference.png` and used as ALBEDO. That is the wrong layer: those pixels already contain the artist's lighting, so the game then added the board's bright ambient, the shader's own emission and the specular sheen on top of them, and the gem always rendered lighter and greyer than the reference — which no amount of re-sampling would have fixed. Three changes, all pushing the same way:
  - the four stops now sit **under** the sampled values and are more saturated (mid went from `(0.17, 0.66, 0.62)` to `(0.055, 0.50, 0.45)`, i.e. HSV saturation **0.74 → 0.89** and value **0.66 → 0.50**);
  - **`saturation` (1.35)** pushes every colour away from grey — the first knob for "make it stronger", and the one to reach for again;
  - **`sheen` 0.9 → 0.35** and **`ambient_occlusion` 0.55**: a broad specular sheen lays white over the whole face, and the board's ambient is the main whitener. (AO belongs to the Forward+ light pipeline and may simply be ignored under gl_compatibility — harmless, which is why the darker stops do the real work.)
  The emission was also weighted to the **top** (`pow(1.0 - t, 1.6)`) instead of being roughly even: an even glow lifted the mid and dark greens, a second reason the gem read pale.
- **"Vivid" is now measured, not opined.** `tests/button_probe.tscn` reports the whole ramp's HSV saturation and asserts the body stop is above 0.85 — `stone ramp saturation: top 0.12 | upper 0.67 | mid 0.89 | deep 0.95` — plus that `saturation >= 1.0` and `sheen <= 0.5`. Subjective words become numbers that can be tuned against, which is the only way this can converge without me seeing the screen.
- **The light moved to the TOP MIDDLE, and the metal band at the ends got wider.** Three requests, two of them geometry:
  - **Wider metal at the ends** (by 2.25×: 0.036 m → 0.081 m per end). The pocket is now inset *further along X than along Z* (`END_BAND = BEVEL * 2.6`), so the bezel is chunky at the capsule's ends while its top and bottom edges stay the same width. Deliberately only the X inset changed: that leaves the stone's z extent — and therefore the shader's `face_span`, which the probe asserts against the mesh — untouched, so the ramp could not be silently compressed by a geometry tweak. The round-over offsets uniformly from the pocket, so the rim's width follows on its own.
  - **The gem darkens toward its sides.** The ramp was a purely vertical one, which made the whole top row equally white. It is now indexed by the **distance from the point the light enters** — the top middle — so brightness falls off downward *and* out toward the ends (`side_spread` 1.9, `vertical_spread` 1.0). That single change is what the request described: a pool of white at the top centre, dispersing to darker green toward the sides and the bottom.
  - **Crystal character.** Two additions, both deliberately subtle: `facet_strength`/`facet_freq`/`facet_dir` modulate soft planes through the stone (multiplied into the ramp, so they add structure rather than painting a pattern over it), and `edge_glow` adds the bright grazing-angle edge that glass has — applied *before* the darker `rim_color` band, which is what gives the stone thickness instead of just a glow.
- **The widened end bands rendered BLACK, because a metal's albedo cannot brighten it.** The frame shader mixed a dark `wall_tint` (0.26) into the *albedo* of any surface facing sideways, to keep the outer wall from going black. That is backwards for a metal: albedo **TINTS** the reflection, so on the end caps — which mirror the horizon and the dark ground — the two multiply, `0.26 x ~0.1`, and come out black. It was double-counted too: the wide end band is mostly the rim's round-over, which curves from facing-up to facing-sideways, so the "is this a wall?" test caught it even though the player sees it from the front. The dark tint is gone; the environment darkens the bevel correctly on its own, and the only thing added is a small **EMISSION lift** (`lift_color`, `lift_strength` 0.12) so nothing can collapse to black whatever it is reflecting.
- **The frame now shares the gem's light.** It ramps on the **distance from the top middle**, exactly like the stone, rather than on height alone — and because both meshes are unwrapped across the whole button, they share one UV space, so "the top middle" is the same point on the same object for the gem *and* its bezel. They cannot disagree about where the light is. The frame gets its own `side_spread` (1.2 against the gem's 1.9) because it spans the entire capsule: the gem's falloff would take the ends all the way to the darkest colour.
- **Now asserted, not assumed:** `metal_bottom` luminance must stay above 0.15 and `lift_strength` above 0 — a direct regression guard for "the sides are black" — plus the frame's `side_spread` must be both positive and *gentler* than the gem's.
- **The rim is now ONE continuous curve, because three pieces read as three planes.** At the ends of the capsule the frame showed three bands — light, grey, near-black — with hard edges between them, which is exactly how it was reported: "this should be one singular face… not as if they are different planes". They *were* different planes: the profile was a flat top band, a quarter-round, and a **vertical outer wall** — and a vertical wall seen from a camera 11° off the vertical reads as a near-black outline following the capsule (the screenshot sampled `#141428` there). The profile is now a **half-ellipse**: from the pocket's top edge, out past the widest point, and back in to the underside, so the surface turns smoothly from facing up, through facing outward, to facing down. One face, whose only shading comes from the lighting. `END_BAND` is its horizontal radius (how wide the metal reads — still the requested 2.25× band) and `RIM_RISE` its vertical one. The arc also went from 6 to **14 segments**: at 6, the shading across the curve was quantized into visible steps of its own.
- **A model change invalidated a shader constant AGAIN, and this time the guard reported it.** Widening the pocket's height inset from `BEVEL` (0.075) to `RIM_RISE` (0.10) changed the stone mesh's z extent from 0.826 to **0.776**, which is the shader's `face_span`. Same class of staleness as the `Background` offset that went unnoticed for a while — but the probe compares `face_span` against the real mesh, so the number was corrected from a measurement rather than from memory. One weakness surfaced: the comparison's 0.05 tolerance was loose enough to pass *before* the re-import, when the cached mesh still had the old extent, so it should be tightened to 0.01.
- **Wider metal ends and a 1.2x wider capsule — both done in the MODEL, not by scaling.** The band at each end went 0.081 → **0.139 m** (`END_BAND` 0.195 → 0.34) and the capsule went 1.372 → **1.646 m**, while the gem stayed at 1.369 m and the height did not move at all. Both had to be generator changes: a non-uniform `Background` scale would stretch the rounded end caps into ellipses, and the text fit follows the meshes' own bounds automatically. Only X moved, so the scale, the vertical half of the text budget and the shader's `face_span` all stayed valid — and the probe's click-box check caught the width change the moment the model was rebuilt, before it was re-imported.
- **The frame now falls to nearly black at the bottom, and the falloff is VERTICAL-dominant.** `metal_bottom` went from 0.34 to **0.045** luminance (top:bottom is now 18.5x) with `vertical_spread` 1.25 — while `side_spread` went *down*, 1.2 → 0.6. That direction matters: the frame spans the whole capsule, so a large side spread drags its ends down along with the bottom, which is exactly what had made them look like separate black planes. `lift_strength` also dropped 0.12 → 0.05 — it exists only to keep the darkest part short of PURE black, and it was still sized for a period when the bottom was meant to be a mid grey.
- **"2D MSAA is not yet supported for GLES3" printed on every button.** `GemButton.tscn` asked for `msaa_2d = 2`, which the Compatibility backend does not implement. Removed; `msaa_3d` stays. The font's jaggedness was a different setting entirely: the text `Control` had `texture_filter = 1` (**nearest**), so the glyphs were being sampled from the font atlas unfiltered. Now 2 (linear).
- **A probe constant replaced by a question.** The button-spacing test hard-coded `Vector2(1.372, 0.392)` and would have gone stale on any resize — the trap that had just caught the click box, a few checks earlier. It now asks the button for `face_size()`.
- **Elongated and shortened, and the frame's black pushed to the bottom edge.** The capsule went 4.20 → **4.60** units wide and 1.00 → **0.88** tall, so at scale 0.392 the button is **1.801 x 0.345 m** (was 1.646 x 0.392) — longer and shorter, which is what "elongate it in the horizontal, diminish the height" describes. Because `END_BAND` held at 0.34, the GEM grew with the capsule: 1.369 → **1.527 m** long, while the metal band at each end stayed 0.133 m. `WIDTH`/`HEIGHT` are re-bound at the point of use in the generator rather than edited at the top of the file, because `planar_uvs()` normalises u by `WIDTH` and the shaders measure their horizontal falloff from `UV.x` — a stale `WIDTH` would rescale that distance along with the geometry. `ramp_curve` 1.7 → **2.6** and `vertical_spread` 1.25 → **1.0**: at half-way down the ramp is now only ~17% of the way to the bottom colour, so brightness holds and the black arrives late, and a spread of exactly 1.0 means the full ramp is reached AT the bottom rather than above it.
- **The font came down 88 → 76** (`GEM_BASE_FONT_SIZE`). The scene's Label size is only a starting point — the script re-fits it in `_ready()` — so the script's constant is the one that actually matters; the scene value was mirrored to keep them from reading as if they disagreed.
- **`face_span` moved for the third time, 0.776 → 0.656**, because the stone's z extent follows the capsule's height. This is the guard working as intended: the tighter 0.01 comparison turns each of these into a measurement rather than a guess.
- **Still open (polish, not blockers):** `gem_button.glb` changed again — this time by both *width and height*, so it needs one more editor pass to re-import before the elongated capsule shows in the match, and `tests/button_probe.tscn` reports it as a click-box mismatch (and a stale `face_span`) until then; the outer silhouette is visibly aliased in screenshots, which MSAA in `project.godot` would fix if wanted; the preview camera was framed for the model alone and may want re-aiming now that the button carries text; the gem's Blender-side roughness/emission (0.15/0.35) affect only the Blender render; the exact colour match still needs an eye on the screen, since the albedo sits under lighting that cannot be rendered headlessly; and the studio softbox cards in the generator are still rendered but no longer exported (the export selects `Frame` + `Stone` explicitly).

#### Crystal Cost Readout ("Pay …"), and reading a sprite sheet without eyes
- **The readout is now actually wired into the game.** It existed as `crystal_cost.tscn` for two rounds before anything created or showed it, so the answer to "I don't see anything" was simply that — an omission, not a bug. It is owned by `Assistant`, appears with the payment modal, sits above the player's hand, and is rebuilt from what is **still owed** (`mana_cost − mana_acc`: elemental first, then whatever is left over pays neutral) every time a crystal is selected. So it counts down as you pay.
  - `remaining_cost()` is now the **single definition** of that arithmetic, and `can_pay_cost()` is just `remaining_cost().is_empty()`. They were two copies of the same element-then-neutral rule, free to disagree about the same selection.
- **Two problems only a screenshot could have found.** (a) *Placement*: the first offset (0.25 y, 1.15 z) put the readout up on the board, overlapping the bottom row of cards — screen-up is 0.985 of +z against 0.174 of +y at this camera angle, so z does nearly all the work. (b) *Scale*: at 0.40 m the accents were fine, but at the 0.22 m it started at, the badge was ~41 px, which made the ring about **one pixel** and the numeral unreadable — a cost read as "Pay [flame] [black dot]". The asset shots had hidden this by filling the frame with a single badge.
- **A Label3D numeral renders in an asset scene and NOT in the game, at any size.** Measured, not guessed: the node reported `text='1'`, `visible=true`, the correct `pixel_size`, correct parenting; it was billboarded and given `no_depth_test`; a 4× zoom shot of its badge showed a blank disc. The cause was never established. The fix was to remove the dependency — digits are now **baked textures** (`tools/build_digit_textures.gd`, rendered from the project's own font 1..20) drawn on the quad through the same path the element glyphs already proved works in both contexts. That is honest workaround rather than diagnosis, and it is written down here as such.
- **Sizing is a property of the SOURCE ART, not a taste.** The new icons are ~26 px, and at this camera's 187 px per metre that is 0.14 m — so they are drawn at roughly their native pixel size instead of upscaled. The "Pay" label is sized from the badge size by a setter, because they have to move together: the label had been towering over the icons, since a setter only runs when something *assigns* the property and nothing ever did, leaving the old 0.17 m default in place.
- **Plain icons, flat discs.** `disc_amount` was added to the badge shader: element badges set it to 0 (the glyph alone, no disc, no ring — the accent ring that looked good at 0.40 m is noise at 26 px), while the numeral sets it to 1 with a white disc and **black** baked ink, and the vignette off so the disc is flat white with no border.
- **THE SHEET WAS READ NUMERICALLY, because the image tool could not open it.** `references/icons.png` came back as "an essentially uniform black field", so `tools/build_element_icons.gd` now prints a **fingerprint for every cell** (size, coverage, mean RGB, hue/sat/val) and dumps the whole sheet as **ASCII, one character per 2×2 px, lettered from each pixel's own colour**. That is how a sprite sheet gets identified with no viewer at all: shapes are visible and every colour is unambiguous. Worth reusing, and much more reliable than describing pixels back and forth.
- **That dump showed the sheet is a SHADED ICON SET, not eight icons:** a 5×5 grid of 25 at a uniform 26 px pitch, in which most glyphs appear several times over — in grey and white as well as their element colour (the snowflake is cyan at cell 11, grey at 12, white at 13). Reading the first eight cells therefore gave grey, grey, white, yellow, orange-red — which is why the "elements are cells 0..7" assumption was wrong.
  - The mapping is now explicit in the tool: **fire 7** (orange flame), **ice 11** (cyan snowflake), **water 14** (blue droplet), **lightning 18** (purple bolt), **wind 21** (green swirl), **earth 3** (yellow slab) — all certain from shape *and* colour. **light 15** (white ring with spokes) and **dark 0** (grey notched slab) are **inferred**, because neither has an element colour; if they are swapped, two numbers change and nothing else.
  - `icons.png` is RGBA, so the icons are **cut out** rather than chroma-keyed: the keying and erode passes that the old JPG needed are gone, along with the pale halo they left around every edge.

#### Element Icons (first attempt, from references/all-element.jpg — superseded above)
- **The icons were EXTRACTED from the sheet, not generated.** `references/all-element.jpg` is 1986x276 — one row of eight cells of 248 px — with the glyphs free-standing on solid white. `tools/build_element_icons.gd` (run as `godot --headless res://tools/build_element_icons.tscn`) keys the white out, trims each glyph to its own bounding box, fits it to a padded square and writes `assets/elements/<element>.png` at 256x256 with straight alpha. The artwork is exactly the sheet's; nothing was redrawn, and the `image-generator` skill was deliberately *not* used — that is for creating art, and re-drawing existing glyphs would cost credits and change them.
- **A JPG has no alpha, so the background had to be KEYED rather than simply cut out.** White maps to alpha 0 and artwork to 1, with a ramp between so the anti-aliased edges stay smooth; the alpha is then eroded by a pixel, because a JPG's ringing at an edge is *lighter* than the glyph and otherwise survives the key as a thin bright rim.
- **The result is checked by eye inside the run itself.** The builder also writes `assets/elements/_contact_sheet.png`, tiling all eight over **magenta** — where a leftover white background, a halo, or a glyph that keyed to nothing is unmissable, and where on the game board it would blend in and be missed. Per element: fire 182x236 mean alpha 0.37, ice 248x231 / 0.41, wind 248x257 / 0.37, earth 248x217 / 0.58, lightning 233x259 / 0.27, water 223x239 / 0.35, light 248x211 / 0.10, dark 204x219 / 0.49.
- **Two findings from that check.** (a) Every glyph carries the sheet's baked soft shadow as a faint halo — that is part of the art, not a keying failure, since the erode only removes a one-pixel fringe; it reads as a soft glow behind the glyph, and stripping it would need a per-element key threshold. (b) `light` is the sheet's white-on-white glyph and comes out at 0.10 mean alpha: present and correctly shaped, but by far the palest, which is apt for the element and worth knowing before it looks like a failed extraction.
- **`element_badge.tscn` + `shaders/element_badge.gdshader` are the circular carrier**: a disc, a thin accent ring in the element's own colour, and the glyph on top — unshaded, because a cost indicator is UI that happens to live in the 3D world and should read the same wherever it floats. `scripts/element_badge.gd` accepts `element` as either the ASCII cost key or the CJK character the cards use (`火`), so a cost Dictionary becomes badges with no translation step in between.
- **`tests/element_badge_probe.tscn` — 24 checks — verifies the plumbing and is explicit about what it cannot**: all eight elements resolve from both spellings, the accent table lines up with the element list, an unknown element resolves to -1 rather than being guessed at, the icon binds and is 256x256, and changing `element` genuinely swaps the texture. The badges' *look* needs a GPU and an eye, so it is asserted nowhere.
- **New assets need one import pass.** Godot cannot `load()` a PNG it has not imported, so `assets/elements/*.png` only become usable after the editor has seen them — or after `godot --headless --import`, which is what was run here (with the editor closed, per the project's rule).
- **Elemental points get ONE BADGE EACH; neutral gets ONE NUMERAL BADGE.** That is the corrected reading of the layout: a player counts off what is still owed badge by badge, so a 2-fire cost is two fire badges — but neutral has no glyph of its own, so it is shown as a single badge with the number in it. Red Mage (2 cost, fire, i.e. `{'火': 1, 'neutral': 1}`) therefore reads **Pay [火] [1]**. Each badge got a second mode for this: `number >= 0` draws a numeral instead of a glyph, via a `Label3D` child sized in metres from the font metrics (height solved from the disc, then shrunk if the text would still be too wide, so a two- or three-digit neutral stays inside the rim). In numeral mode the glyph sampler is pointed at a **fully transparent 1×1** rather than left holding whichever icon was set last — cheaper and safer than a shader branch, and it keeps the disc/ring path identical in both modes.
- **`crystal_cost.tscn` is the row**: "Pay", then the elemental badges, then the neutral numeral — laid out along local +x, which is screen-right once the row faces the camera, and centred on the node. It takes a cost Dictionary in exactly the shape `Card.get_cost()` produces, **including its habit of keying elements by a one-element Array (`["火"]`)** — that would have silently produced nothing, so `ElementBadge.key_to_element()` normalises both spellings and the probe tests both.
- **Both the row and each badge turn to FACE THE CAMERA**, by adopting the camera's basis while keeping their own position. It is done on the node rather than as a shader billboard on purpose: a shader billboard would turn the disc but leave the `Label3D` numeral behind, and the two would drift apart as the camera moved. A quad's face is +Z, which is what points it at the viewer.
- **The probe caught a real bug immediately.** `_rebuild()` used `queue_free()` alone, which is *deferred* to the end of the frame — so the old badges still answered `get_children()` and were counted alongside the new ones. Every re-set of `cost` doubled the row; only the first case passed, which is exactly the failure signature that points at deferred removal rather than at layout maths. The fix is `remove_child()` (immediate) followed by `queue_free()` (deferred): removing from the tree has to be immediate, freeing does not.

#### Gem Button: Lighting and Materials
- **Buttons slide in from the right instead of appearing out of nowhere.** The three knobs are `@export`ed at the top of `scripts/gem_button.gd` (and therefore also in the Inspector, per instance): **`slide_in_duration` 0.5 s**, **`slide_in_distance` 2.4 m**, and the curve, **`slide_in_trans` TRANS_CUBIC / `slide_in_ease` EASE_OUT** — "fast at the start, smooth at the end". `TRANS_QUINT` or `TRANS_EXPO` with `EASE_OUT` is more dramatic, `TRANS_QUAD` with `EASE_IN_OUT` gentler, `TRANS_BACK` with `EASE_OUT` overshoots slightly.
  - **It turns over as it arrives: 180° about x, the same axis it travels along,** so the button comes in showing its BACK and rolls face-up to reveal the gem and the label. `slide_in_flip_degrees` is the knob — try 90 for a quarter turn, 360 for a full roll, 0 to disable. The flip rides the same curve as the slide and is the second tweener of a `parallel()` pair; chained tweeners would run one after the other, sliding the button in and only then turning it.
  - **No culling tricks were needed — which was worth checking rather than assuming.** While the back faces the camera the button would be invisible under `cull_back` *if* the mesh were a flat card, and the first instinct was to flip the shaders to `cull_disabled`. But rotating a node rotates its normals with it: at 180° the button's UNDERSIDE becomes the front-facing surface and renders normally, while the gem/label side is culled in its place. That is also what hides the label's quad — the content is not dimmed, it is simply not drawn. Verified through the UP VECTOR rather than an Euler angle (`up.y -1.000` at the start, `+1.000` at the end), because "back face to the camera" is a physical statement and a 180° turn can legitimately be reported as ±180.
  - Hiding snaps the rotation back along with the position, so a hidden button is never left face-down.
  - **The pair is staggered, and sits closer.** `slide_in_delay` (declared next to `slide_in()`, because it is a property of the PAIR rather than of the movement) postpones a button's whole entry: Cancel carries **0.1 s** as an instance override in `game.tscn`, so when a modal opens the second button starts a beat after the first instead of the two moving as one slab. Confirm and PassPhase stay at 0. The offset and the turn are applied *before* the tween's interval, so a delayed button waits already off-screen and turned over rather than sitting in its slot and then jumping.
  - Cancel's slot moved 0.47 → **0.42** along −z, so the gap between the two buttons is **7.5 cm** rather than 12.5 — tight enough to read as one pair.
  - The stagger is asserted by **distance travelled, not by reading the delay back**: both buttons are shown, both tweens stepped half the delay, and then the first must have moved (>0.2 m) while the second has not moved at all (0.000 m). A test that re-read the parameter would pass even if the interval were never applied.
  - The offset is a **local** x, not a new position: it settles back to the slot captured in `_slot_position`, so the rack still owns where the buttons live and the main-slot rule is untouched.
  - It starts **off-screen**, and the distance is derived rather than guessed: the orthographic camera's visible width is 10.25 m, so its right edge is at x = −5.125, and a button whose half-width is 0.90 only clears that once it starts 2.23 m further out. 2.4 leaves a margin. Screen-right is world **−x**, so the offset is negative.
  - The hook is **`NOTIFICATION_VISIBILITY_CHANGED`**, not an override of `show_button()`: that covers `BigButton.show_button()` and `hide_button()`, anything a future caller does, *and* toggling the Inspector's `visible` checkbox while `GemButtonPreview.tscn` runs — which is the quickest way to try the parameters.
  - Hiding stays instant (no exit animation): a button lingering over the board on its way out reads as a stuck one. It also snaps back to the slot, so the next show starts from the edge again.
  - Caught while testing: the first version of the check waited on `Engine.time_scale` and a scaled `SceneTreeTimer`, and the button never moved — headless frame deltas are tiny, so the timer resolved having advanced the tween almost none of its duration. The probe now drives the tween with `Tween.custom_step()` after `pause()`, which advances it by an exact amount regardless of frames or wall-clock. Measured: `starts at x -2.400 with the slot at +0.000 (duration 0.50 s)` → `settles at x +0.000`.
- **The buttons now hang off a `ButtonRack` node, which is the ONE place their position lives.** The question that prompted it — "is there not a way to make them all share the same position without doing it manually?" — had a real answer, because the shared x/height was written into all three children by hand and they drifted the first time one was edited alone. Now `Assistant/ButtonRack` owns the shared transform and the buttons carry only their SLOT offset:
  - `ConfirmButton` and `PassPhaseButton` have **no transform at all** (identity), so they are the same slot *by construction* rather than by two numbers agreeing;
  - `CancelButton` is `(0, 0, -0.47)` — the second slot, 0.47 along −z where the button measures 0.345;
  - so moving all three is one transform, and the main-slot rule cannot be broken by editing one button.
  The cost was mechanical: `assistant.gd`'s three `$ConfirmButton`-style lookups and the probe's paths went through `ButtonRack` (verified: no `Assistant/` paths remain in the game scripts). New assertions pin the structure: all three share that parent, and PassPhase == Confirm, Cancel != Confirm. x is now **−3.8** (spanning 78–96% of the width, a ~4% right margin) — a nudge back from −4.1, and it re-unifies the three, which had ended up at −3.93 / −4.1 / −4.1.
- **The main slot, and the buttons moved out to the right edge.** Confirm and PassPhase now share the position `(-4.1, 0.327, -2.0)` *exactly*: the pass-phase button takes Confirm's slot, so closing a modal does not move the button the player was just looking at — and Cancel's slot is simply left empty. That is a layout contract, so `tests/button_probe.tscn` asserts it (PassPhase == Confirm, Cancel != Confirm) rather than leaving it as a coincidence that two transforms happened to share.
- **Where the "large right margin" came from, measured rather than guessed.** The camera is **orthogonal** (`projection = 1`) with a vertical extent of 5.766 m on a **1920x1080** viewport, so the visible width is 10.25 m — and screen-right is world **−x**, because the camera's `basis.x` is `(-1, 0, 0)`. At the old x = −3.05 the 1.801 m button sat at **71–88%** across, leaving an 11.5% strip of empty board on the right; at **−4.1** it spans **81–98%**, a ~1% margin. Both numbers come from the projection, not from trial and error — and had the basis not been checked, the shift would have been a coin flip in the wrong direction.
- **The root cause was the environment, not the model.** `game.tscn`'s `Environment` used a `PanoramaSkyMaterial` with **no panorama assigned**, so the sky was black — and with `reflected_light_source = 2` (Sky) every metal surface was reflecting *nothing*. On top of that `ambient_light_sky_contribution` was `0.0`, discarding the sky's ambient entirely. A mirror with nothing to mirror cannot look like a mirror, so no material value could ever have fixed it. Replaced with a **`ProceduralSkyMaterial`** — a studio gradient (bright overhead `0.92, 0.95, 1.0`, mid horizon, near-black ground), ambient sky contribution `0.6`. Measured luminance ratio top:ground **43×**, which is the gradient that draws the reference's bright top rim and dark lower band.
- **Materials exist now**: `gem_button_metal.tres` (full metal `metallic 1.0`, `roughness 0.12`, cool silver albedo) and `gem_button_stone.tres` + `shaders/gem_button.gdshader` (a vertical "lit from within" gradient, emission modulated by it, and a fresnel rim that darkens the silhouette). The shader deliberately **fakes** translucency: `transmission` is Forward+ only and this project runs `gl_compatibility`, so the cabochon read is built from gradient + emission + fresnel instead of refraction.
- **Why the glb's own materials were wrong**: the export carried `metallicFactor 0.465 / roughnessFactor 0.5` for the frame (grey plastic) and an **opaque green** for the stone. glTF **cannot export Blender's Specular/Coat/Sheen channels at all** — they are dropped silently, which is very likely what "I could never get it right" was: the gloss was being set in channels the exporter does not read.
- **`GemButtonPreview.tscn`** — a standalone scene (model + the same studio sky + a key light from above-left + a camera) to judge the material and lighting without booting a match. `scripts/gem_button_model.gd` walks the instanced glb and applies metal/stone per mesh (a `.tscn` cannot reach inside an instanced scene, which is why a script does it), identifying the stone by node name or, failing that, by its material being non-grey.
- **`tests/button_probe.tscn`** — asserts the sky is a `ProceduralSkyMaterial` (not an empty panorama), the ambient sky contribution is non-zero, reflections come from the sky, the top:ground luminance ratio is large, the frame is a full metal at low roughness, the stone emits, and both meshes are identified. It also proves the `;` comments in the `.tscn`/`.tres` files parse.

#### The Stack: Fan, Hover, and Review Links
- **Fixed: the review arc was drawn in "random places".** It was parented to the **Stack**, but `BallisticArrow` treats the points it is handed as **LOCAL** coordinates — and the stack node is flipped and lifted above the board, so global points got carried by that transform. The live targeting arrow and the block arc never had the bug because both live on the **Field**, whose frame is identity, so global points happen to be correct there. The review arc now belongs to the Field too (`Field.show_review_link` / `hide_review_link`), and the probe asserts **where** it is drawn, not merely that it exists: the mesh's first vertex must sit at the source card's top edge. Measured gap `0.0350` = exactly the `arc_height` lift, for the top card and again for the hovered one.
- **The stack is laid out like a hand, hanging to the left.** `Stack._slot_for()` reverses the index so the TOP of the stack (`cards.back()`) is the leftmost card and each earlier card steps right; the arc, the tilt and the stacking height all derive from it, so they cannot disagree about which end is which. `FAN_TIGHTNESS = 0.5` halves the pitch — measured `x = ±0.164` for two cards, was `±0.328` — because a stack should read as one group, not a spread-out row. The top is also the highest, so it is in front as well as on the left.
- **Stack cards are clickable now.** `Card._update_state()` assigned `current_state = null` for any parent that was not a Hand or a Field, so a click on a stack card did nothing at all. `StackCardState` (mirroring `HandCardState`) raises a clicked card (`FAN_RAISE`) and selects it. Hover goes through `Card._on_card_area_3d_mouse_entered/_exited` — methods `card.tscn` had been connecting all along that simply did not exist — and is forwarded to `Stack.set_hovered()`.
- **The review link: hover a stack card and see ITS target.** Every stack card keeps the target it was given (`Card.effect_target`), so the stack can re-draw any of those links. The card on display is the one under the mouse, and otherwise the **top of the stack** — hover is transient, so there is no "clicked elsewhere?" rule to maintain. It is DISPLAY ONLY: no session, no state change.
- **DESIGN POINT: the review link draws the ARROW ONLY — never the aura.** The aura already has an owner (the live pick, plus the red reveal that holds until the stack resolves), and an earlier version of the link painted it too. Because "clear only what I lit" is indistinguishable when two writers light the *same* card, the link stole the reveal's ring and then cleared it: the probe went from `opponent chose Zack (red=true)` to `(red=false)`, failing three checks that had been green. Ownership is explicit now — the link releases its arrow at the START of any targeting session (`Field.request_target()` → `Stack.release_target_display()`), and since the arrowhead lands exactly on the target, the link reads without a second signal. If a hover aura is wanted later, the correct change is to make the aura DERIVED in one place that decides which card is marked and why — not to add a third writer.
- **A new `class_name` is invisible to a headless run.** `StackCardState` failed to parse with `Identifier "StackCardState" not declared`: Godot's global class cache is only regenerated by the **editor**. `card.gd` now uses `const STACK_CARD_STATE := preload("res://scripts/stack_card_state.gd")`, which does not depend on the cache. That single parse error produced 9 collateral failures across the other two probes — one root cause, loud and specific, which is the harness working as intended.

#### Green: "You May Activate This Now"
- **A fourth meaning on the same ring: GREEN = the card's effect is available to activate.** It shows on your cards only, and only in a moment when you genuinely could: it goes dark the instant a targeting or payment modal opens, and equally when the window is not yours. That is what makes the cue honest rather than decorative — it answers "can I do this *right now*", not "does this card have an ability".
- **Green is drawn at HALF the ring's width** (`Card.AVAILABLE_WIDTH_SCALE = 0.5`, applied to `border_width` and `glow_width` together). It is a *standing* cue — it can sit on several cards for a whole turn — whereas blue/orange/red are momentary, so a thinner ring keeps it subordinate to them instead of competing. The stock widths are cached at build time (`_border_width_base` / `_glow_width_base`) and every other state restores them exactly, so switching between states cannot accumulate a drift: measured `green=0.0125 | stock=0.0250`, and `0.0250` again the moment another state takes over. If only the band should shrink and the spill should stay wide, scale `border_width` alone.
- **"The mode allows acting" is not the same as "the window is yours."** The first cut gated on `FREE`/`INSTANT_SPEED_TIME` alone, which is satisfied *while the opponent holds priority* — the mode reflects what UI is available, not who is being asked. `Field.has_priority()` (→ `Game.priority_holder == 1`, and not after the match ends) now closes that hole, so the ring cannot glow while the human is unable to act. The lesson generalises: when a cue claims availability, it has to be driven by the same conditions as the action, not by a proxy like the input mode.
- **The gate is shared with the action, not copied.** `Field.can_activate_now(card)` — your card + **your window** + untapped + has a non-empty `skill` + mode is `FREE` or `INSTANT_SPEED_TIME` — is now the precondition of `begin_skill_activation()` **and** the source of the ring, so the cue and the action cannot drift apart (the old four `if ... return` guards lived only inside the action, exactly the kind of rule that goes stale when copied). Adding a condition here tightens both at once.
- **It is polled, not hooked.** `Field._process()` recomputes every `AVAILABILITY_POLL` (0.15 s) via `refresh_available_effects()`. Unlike the other rings, availability is *derived* state with many causes — the input mode, the priority holder, a card's tapped state, the field composition — and a single trigger would have missed cases; the card setters are guarded, so an unchanged card costs one bool comparison. If it ever needs to be instant, the honest change is to call `refresh_available_effects()` from `GlobalVariables.player_mode_change` rather than to add hooks piecemeal.
- **The ring became one object with four meanings** (`_prompt_glow` blue, `_selected_highlight_on` orange, `_targeted_highlight_on` red, `_available_highlight_on` green) with `Card._refresh_target_ring()` as the single owner of colour and visibility: lit if ANY meaning is on, coloured by priority orange > red > green > blue. Four independent writers on one material meant the last setter decided the colour, and one of them (red) could only recolour a ring nothing had lit — the bug that shipped. `set_highlight()` is now the renderer alone; `Hand.refresh_highlights()` uses the new `set_prompt_glow()` so the hand and the field share one "the game is asking you" flag. `Card.enter_zone()` clears **all four**, so a green or red ring cannot ride into the graveyard.
- Verified in `tests/flow_probe.tscn`: `green with the targeting modal open: []`, then with nothing pending `red mage=true (lit=true) | any opponent green=false` — the three requirements in one line each.

An activated ability (Red Mage) whose target (Squall) resolved and was not followed by another targeting left that card glowing orange for the rest of the match. `reset_targets()` now clears all three. #### Targeting Arrow (rebuilt)
- **The arrow is a generated ribbon plus a real arrowhead**, not a row of spheres. `ballistic_arrow.gd` builds a `Curve3D` from the source card's TOP EDGE to the target card's CENTRE, tessellates it, and emits a unit-width triangle strip whose per-vertex UVs and COLORS carry everything the shader needs (`UV.x` = position along the arc, `UV.y` = which edge, `COLOR.rgb` = the sampled `side` vector, `COLOR.a` = the arc position again). `shaders/target_arc.gdshader` scales the strip out along that baked side in `vertex()` and paints it additively in `fragment()` (bright core + halo falloff across `UV.y`, plus a wave travelling along `UV.x`). The head is separate real geometry — a notched spade whose base is the shaft's **last sample** — sharing the same fragment look so it matches the shaft instead of reading as a decal. `shaders/target_arc_material.tres` is the look; widths and head proportions live on the node.
- **WHY THE EARLIER CUTS LOOKED WRONG — three separate geometric causes, each worth remembering:**
  1. **The camera looks almost straight down** (~10° off vertical), so an arc that rises in **world Y** is foreshortened to nothing and reads as a **straight line**. The bow has to happen in the **screen plane** (the camera's own axes flattened onto the board) — which is also the only reason the original sphere version looked curved at all, via its `Vector3.RIGHT * 1.4` swing.
  2. **The curve was two Bezier segments with a handled midpoint**, and those interior handles reinstate a **second extremum** — the S-shaped wiggle. With ONE segment whose two controls both lie on the screen-up axis, the up-coordinate's derivative has exactly one root inside (0,1) for every separation (checked for D>0, D<0, and D=0 where it degenerates to t=1/2). `peak_ratio` is now the user-facing knob and the handle is derived from it (`h = peak_ratio / 0.75`); equal controls also keep the control polygon convex, which is what guarantees no inflection.
  3. **The head was a straight back-off from the tip** (`tip - tangent * length`), which lands *off* the curve on a curved approach — hence the head looking detached. It is anchored to the shaft's last sample now.
- **The shape is asserted at runtime, not assumed.** `BallisticArrow._check_shape()` counts apexes along the screen-up axis and inflections in the screen plane, prints `curve shape OK: 1 apex, 0 inflections, peak N.NNx the card distance` once, and `push_warning`s (de-duplicated, so it cannot flood while dragging) when either is wrong. A mesh rebuilt every frame would otherwise be a silent, repeating defect.
- **Two traps that would have looked like "mysterious deformation":** Godot stores vertex `COLOR` as **8-bit UNSIGNED normalized**, so a baked side vector with a negative component clamps to 0 and deforms the ribbon — the CPU bakes `side * 0.5 + 0.5` and the shader decodes it (guarded with `max(length, eps)` against NaN). And because the *shader* expands the mesh, the mesh's own AABB is far too small, so `extra_cull_margin` is required or the renderer culls the arrow away.
- **Draw order and height.** `side = tangent × UP` is always horizontal, so the ribbon sits in the **board plane, exactly level with the card faces** — and co-planar additive geometry is at the mercy of sorting. The material now uses `render_priority = 100` (every card material is 0) and `arc_height` (0.035 m) lifts the whole arrow clear of the board as a pure translation.
- **The apex is kept inside the window.** `_peak_ratio_for()` solves for the tallest arch that still leaves `screen_margin` (90 px) below the top edge: it projects the chord's midpoint and a point one metre further along the screen-up axis to get px-per-metre, then derives the allowance, floored at `MIN_PEAK_RATIO` (0.2) so a source near the top of the screen still gets a bend rather than a straight line. It only ever *reduces* `peak_ratio`.
- **A stack effect's arrow originates from the effect card IN the stack.** `Field.execute_card_effect()` asked for the target with the card on the **field**, even though `Stack.create_card()` had already made the copy the effect actually resolves as. It now passes that copy (`_stack_effect_card_for()` matches on `effect_source`, falling back to the field card rather than failing).
- **The origin is followed rather than frozen** (`set_is_aiming_from_card()`). A freshly created stack card is positioned through a **0.3 s Tween** (`Stack.update_card_positions()` → `animate_card()`), and `add_created_card_to_tree()` sets `global_transform` to the transform captured *before* `add_child` — so at the moment targeting starts the card is still at **world (0,0,0)**, which a top-down camera projects to the **middle of the screen** (the reported bug). The arrow re-reads the card's mid-top every frame, so it stays attached while the card settles and if it moves later.
- New `Card.get_global_top_centre()` — the mid-point of whichever edge projects higher on screen, so it is correct for any rotation or fan tilt — and `Card.get_global_face_centre()`. Note `Card.get_global_center()` is **not** the centre: it adds a fixed `(0.2, 0.3, 0)`, and is left alone because other callers depend on that behaviour.
- Glow refinements on top of the CSS re-model: opacity now grades with distance from the card (`border_alpha` at the inner edge → `border_alpha_far` at the outer, then the feather), the pulse is faster and shallower (`pulse_speed` 4.5, `pulse_amount` 0.25, `pulse_width` 0.18 with the slider allowed past 1.0 to swell several times), and the per-target marker that used to be spawned above each candidate was removed — the prompt glow is the only targeting cue.

#### Opponent AI (Phase 3, first pass)
- `AIAgent.decide_attacker()` — tap-economy judgement. Attacking taps a Forward, so it cannot block on the opponent's next turn: the AI reserves a blocker (cheapest Forward that can still beat the opponent's best untapped Forward, else its strongest) and attacks with the strongest remaining Forward that does not trade down — strictly smaller than their best is skipped, equal power is allowed as an even trade.
- `AIAgent.decide_blocker()` — blocks only with a strictly bigger untapped Forward (equal power breaks both), preferring the smallest such card. Blocking is then free: the blocker takes less damage than its own power, and the attacker breaks.
- `AIAgent.choose_target()` — picks the strongest legal target (groundwork for Summons; still unreachable, see Known Issues).
- **The AI now plays cards.** `AIAgent.take_priority()` plays an affordable card from its hand during its own main phases.
- **Matches can now end.** `PlayerSide` exposes `damage_count()` / `is_defeated()` and emits `damaged(self)` from `take_damage()`; `Game` listens (via `game.tscn`, both `Player` and `Opponent`) and calls `_end_match()` at `DEFEAT_DAMAGE` (7) cards in the damage zone, or when the deck cannot supply the cards for the damage. `_end_match()` sets `match_over` — checked by `next_phase()`, so the phase machine stops — writes the result to `$PhaseText` and returns to the menu. Because the check hangs off the signal, every damage source (attacks and effects) is covered without touching the call sites.
- **The human can block.** New `Player_Mode.BLOCKING`: during `BLOCKER_DECLARATION` the local defender clicks their own untapped Forwards to select one (highlighted via the new `Card.set_blocker_status()`) and a `Block` / `No Block` button ends the declaration. `LocalAgent.decide_blocker()` returns `Field.blocker_card`, so the existing `declare_blocker()` → clash path is reused unchanged. The mode is pushed only for a local defender, and `Game._on_field_blocker_changed()` is gated on it — `blocker_changed` fires for both sides, exactly like `attacker_changed`.
- `Agent` gained `pay_cost()` (return whether a cost is covered) plus `choose_target()` / `choose_card_in_hand()` — the "drive the UI" seam, where a non-local agent performs the clicks a human would have made and the existing signal continuation carries on. `Field.request_target()` delegates to it for non-local owners so targeting can never leave the turn waiting for a click.
- `Game.play_card_for(player_id, card)` — plays from any hand: charges the card, has non-local owners pay via `Agent.pay_cost()`, then completes the payment itself with the human's modal buttons hidden.
- `Field.get_front_cards_for()` / `get_back_cards_for(controller)` — read accessors so agents don't reach into the raw arrays.

### Fixed

- **The priority model was wrong: a player could act twice with their own effect still unresolved.** `Game.priority()` restarted every round with `turn_owner` first, so whoever had just played was handed priority straight back — on the practice board the AI cast **Ifrit** and then played **Dark Knight** while Ifrit was still on the stack, and the human's priority window arrived after the second play. Rewritten to the FF TCG model: the turn player receives priority first in a phase/step; **performing an action hands priority to the other player** (`Agent.take_priority()` now returns whether it acted — a played Character never touches the stack, so stack growth could not detect it); two consecutive passes with no action between them resolve the top of the stack, after which the **turn player** has priority again, or advance the phase when the stack is empty. A local player's window now ends when they act, not only when they press pass (`Game.priority_window_ended(acted)` ← the pass button or `Stack.note_action_taken()`), which also closed the old hole where the human could add twice inside one window. Fixed with it: **a Character may only be played by the turn player and only with an empty stack** (`Hand.can_play_character()` enforced in `Hand.charge()` and asked by `Card.can_be_played()`) — the rule that stops a Forward landing on top of an unresolved Summon.
- **A card awaiting its cost is only *parked*, not on the stack.** `Stack` now separates "parked" (a visual placeholder while the cost is being paid: `Stack.park_card()`, referenced by `casting_card` / `summon_casting_card`) from `Stack.cards` ("legally on the stack"). `_on_hand_charge_start()` no longer calls `add_card_to_tree()`, so a character card (Forward/Backup) **never** enters `cards` — `cast_card()` plays it straight to the field and there is nothing to pop. Only a Summon becomes a stack object, at `_commit_summon_to_stack()` after payment + target. Stacked on the earlier bug: `Stack._on_assistant_charge_cancelled()` used to pop a real card off `cards` and leave it parented to the Stack (frozen on screen). `game.tscn` also now wires `Opponent/Hand` to Assistant's `charge_cancelled` / `charge_complete` / `target_cancel` / `selected_cards_for_mana_has_changed` — without `charge_cancelled` a cancelled payment could not be returned to hand at all. And `AIAgent.take_priority()` gained a cheap `_can_afford()` total-mana check so it no longer starts payments it cannot finish. Side effect: `stack_length()` (which the priority loop uses to tell whether an action happened) is no longer inflated during a payment window. Layout follows the same split: `Stack.layout_cards()` (= `cards` + the parked card) is what `calculate_total_width()` / `update_card_positions()` read, because deriving the row from `cards` alone left the parked card out of the width and offset every card — which is why a card awaiting payment sat visibly off-centre. `_on_assistant_charge_complete()` re-lays out once the parked card leaves for the field.
- **`Card.reset()` crashed when a card had no mana crystal.** The "selected as a mana source" marker (`crystal_instance`) was created *only* by the two click handlers in `field_card_state.gd` / `hand_card_state.gd`. A card selected any other way — e.g. `AIAgent.pay_cost()` tapping Backups straight through `Field.add_card_to_mana_conversion()` — had a null crystal, and `reset()` (run on every payment completion) dereferenced it: `Invalid call. Nonexistent function 'queue_free' in base 'Nil'`. The marker now belongs to the `Card` (`show_mana_crystal()` / `clear_mana_crystal()`, both null-safe), `Field` / `Hand.add_card_to_mana_conversion()` create it, `remove_*` / `reset()` clear it, and the click handlers no longer touch `crystal_instance` directly — one creation site for the human and for agents.
- **Player damage went to the wrong player.** `Game.cause_damage()` unconditionally damaged `opponent`, which was only correct while the human always took the turn. Now damages `side_for(3 - turn_owner)`, so an opponent attack actually hits the human (and `side_for()` is used instead of sitting idle).
- **Blocking never worked end to end.** `Card.declare_blocker()` emitted `clash_attacker_blocker` immediately, and `Game._clean_instruction_stack()` then nulled `_current_blocker_card` before `DAMAGE_RESOLUTION` read it — so a declared block would clash twice *and* still count as unblocked. Now `declare_blocker()` only records the blocker, persisted as `Field.blocker_card` (which survives instruction cleanup), and the single clash happens in `DAMAGE_RESOLUTION`. `clash_attacker_blocker()` / `cause_attacking_damage()` read `Field.blocker_card` too.
- **An Attack button appeared during the opponent's turn.** `Field.attacker_changed` fires for the opponent's attacker as well (both sides share one `Field`), and `Game._on_field_attacker_changed()` offered the human a button for it. It now returns early unless `player_mode == ATTACKING`, i.e. only while the human's own declaration is open.

- **Target clicks weren't validated.** `Field.set_target_card()` accepted a click on *any* card; `is_valid_target` only controlled the on-card indicator, so Zidane could still be selected even when not highlighted. It now bails unless the candidate is a legal target.

- **Break on equal damage.** `Card.is_broken()` used a strict `>` comparison, so a Forward with damage exactly equal to its power (e.g. 4000 damage on a 4000-power Forward) survived instead of breaking. Now uses `accumulated_damage >= power`.

### Known Issues / Unfinished Work

- **Back Attack is not implemented.** The non-turn player cannot play a Character from hand (only Summons and abilities), so dropping a defensive Character mid-combat is impossible.
- **The AI has no long-term plan.** It plays the first affordable card it sees (no plan beyond mana), skips any card whose enter-the-field effect needs a target (ETB targeting runs mid-resolution, and a miss there is not recoverable yet), and never blocks an equal-power attacker (an even trade is declined rather than evaluated). The human's blocking is unrestricted by comparison — any untapped Forward may block, even one that would break.
- **`choose_card_in_hand()` is not wired to anything yet.** `Game._resolve_may_play_for_free()` and `Stack.begin_s_cost_selection()` still own the choose-card modal directly; a non-local agent would need those routed through the seam.
- **Decklists are fixed** (`standard` uses cards 1-50 vs 51-100); the *order* is now shuffled and seeded, but there is no deckbuilding. `DRAW_PHASE` also still silently skips the draw on an empty deck rather than treating it as the loss it is (`take_damage()` does report running out of deck, so only the draw case is unwired).
- **Power-reduction effects do not re-check state-based actions yet.** A negative `power_change()` can drive a card to 0 power without `enforce_game_state_rules()` running immediately (it is picked up the next time instructions finish or a clash occurs). `Card` has no reference back to `Game`, so this needs a callback or a field-level check.
- **`unbreakable` does not stop power-0 removal** — by design, since power 0 is not a break. (`card_effects.json` `"32"` is Chemist 1-032C, a 0-power Backup whose ETB grants `unbreakable` to a Forward.) Note that Backups store `"power": "0"` in the card database, so the zero-power / breakable scans deliberately look at `front_cards` only; scanning all cards would delete every Backup.
- **End-of-turn abilities have no window before cleanup.** `END_PHASE` runs `Field.end_phase_cleanup()` immediately; there is no priority round for "at the end of the turn / until end of turn" auto-abilities to resolve first (as the real End Phase requires). Needs a priority window in `_enter_phase(END_PHASE)` once such abilities exist.
- **Planet Protector's effect is not implemented.** Aerith's S-ability entry has an empty `instructions` array; the S + dull cost flow works, but activating all Forwards / protection from Summons and abilities is not scripted yet.
- **`activated_ability` keyword is not wired.** Card 8 in `assets/card_effects.json` uses `activated_ability`, but the field flow only activates `"skill"`. Either rename the key to `"skill"` or extend `try_activate_from_field()`.
- **Legacy dead code remains:** `scripts/ManaCost.gd` (live path uses a plain Dictionary), `stack.process_next_effect()`, and `game.pop_stack()` / `stack.pop_stack()`. Since Phase 2 these are also unused: `game.MOCK_opponent_pass_piority()`, `game.TEST_blocker()` / `pass_priority()`, `field.untap_all_cards()`. Kept intentionally in case they are unfinished work.
- **`card_effects.json` coverage is still tiny** compared to the card database. The instruction system, choose-card system, conditional power, and S-cost data are ready for more entries.
